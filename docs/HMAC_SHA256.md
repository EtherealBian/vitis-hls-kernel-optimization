# 第一问：HMAC-SHA256 原代码功能与优化说明

## 1. 项目与文件说明

第一问测试的是 Vitis HLS 中的 **HMAC-SHA256** 算子，测试顶层函数为 `test_hmac_sha256`，目标器件为 `xc7z020-clg484-1`。本次实际修改的核心文件是 SHA-224/SHA-256 底层实现 `sha224_256.hpp`：

- 基线代码：`baselines/security/sha224_256.hpp`
- 优化代码：`security/L1/include/xf_security/sha224_256.hpp`
- HLS 综合报告：`security/L1/tests/hmac/sha256/reports/csynth.xml`
- C 仿真日志：`security/L1/tests/hmac/sha256/reports/csim.log`
- C/RTL 协同仿真报告：`security/L1/tests/hmac/sha256/reports/cosim.rpt`

虽然修改的是 SHA-256 底层模块，但它会直接影响 HMAC-SHA256 的性能，因为 HMAC 的核心计算为：

```text
inner_hash = SHA256((K ⊕ ipad) || message)
HMAC       = SHA256((K ⊕ opad) || inner_hash)
```

也就是说，每条 HMAC 消息至少需要调用两次 SHA-256，因此 SHA-256 数据通路的延迟、吞吐率和时钟频率会直接决定整个第一问的成绩。

---

## 2. 原代码实现了什么功能

### 2.1 对外接口

原代码同时提供 `sha224()` 和 `sha256()` 两个模板接口。输入、输出均采用 `hls::stream`：

- `msg_strm`：输入消息数据流，支持 32 位或 64 位数据宽度；
- `len_strm`：每条消息的字节长度；
- `end_len_strm`：输入消息结束标志；
- `hash_strm`：224 位或 256 位哈希结果；
- `end_hash_strm`：输出结束标志。

SHA-224 和 SHA-256 共用同一套压缩逻辑，主要区别是初始哈希常量不同，以及 SHA-224 只输出前 7 个 32 位状态字，而 SHA-256 输出全部 8 个状态字。

### 2.2 原代码的数据流结构

原来的 `sha256_top()` 使用 `#pragma HLS DATAFLOW`，将计算划分为三个阶段：

```text
输入消息
   │
   ▼
preProcessing
消息分块、补位，输出 SHA256Block
   │
   ├── 块数及结束标志 ──► dup_strm ──┬─► generateMsgSchedule
   │                                  └─► sha256Digest
   ▼
generateMsgSchedule
生成每个块的 W[0..63]
   │
   ▼
sha256Digest
执行 64 轮压缩并输出哈希值
```

三个主要阶段的功能如下。

### 2.3 `preProcessing()`：消息分块和补位

SHA-256 每次处理一个 512 位块，即 64 字节。原代码先根据消息长度计算总块数：

```cpp
uint64_t blk_num = (len >> 6) + 1 + ((len & 0x3f) > 55);
```

其中：

- `len >> 6` 是完整 64 字节块的数量；
- 至少增加一个补位块；
- 如果剩余数据超过 55 字节，则当前块无法同时容纳补位和 64 位长度字段，需要再增加一个块。

随后按照 FIPS 180-4 规则进行补位：

1. 在消息末尾添加一个 `1` 比特；
2. 继续补 `0`，使数据长度达到 448 mod 512；
3. 在最后 64 位写入原消息的比特长度。

代码分别处理三种尾部情况：

- `left == 0`：消息刚好在 64 字节边界结束，新建一个完整补位块；
- `left < 56`：尾部数据、补位和长度字段可放进同一个块；
- `left >= 56`：尾部数据和补位放在第一个块，长度字段放在第二个块。

输入数据还会由 HLS 常用的小端字节排列转换为 SHA-256 规定的大端字序。完成后，原代码把 16 个 32 位字封装成 `SHA256Block` 并写入 `blk_strm`。

### 2.4 `generateMsgSchedule()`：生成消息调度字

每个 512 位消息块只有 16 个原始字，但 SHA-256 压缩函数需要 64 个消息调度字。原代码先从 `SHA256Block` 复制并发送前 16 个字：

```text
W[0], W[1], ..., W[15] = 当前消息块的 16 个原始字
```

然后使用 16 字滑动窗口生成后 48 个字：

```text
W[t] = σ1(W[t-2]) + W[t-7] + σ0(W[t-15]) + W[t-16]
```

生成的 64 个 `W[t]` 依次写入 `w_strm`，供压缩模块消费。

### 2.5 `sha256Digest()`：执行 SHA-256 压缩

该模块根据哈希类型初始化 8 个状态字 `H[0..7]`。对每个 512 位块执行 64 轮压缩，每一轮由 `sha256_iter()` 完成：

```text
T1 = h + Σ1(e) + Ch(e,f,g) + K[t] + W[t]
T2 = Σ0(a) + Maj(a,b,c)

a' = T1 + T2
e' = d + T1
其余状态字依次移位
```

每个块的 64 轮结束后，将工作变量重新累加到 `H[0..7]`，实现多块消息之间的链式计算。所有块处理完毕后，代码完成字节序转换并输出 224 位或 256 位哈希值。

原代码已经对关键数组使用完全分区，并对 64 轮循环设置 `PIPELINE II=1`，因此基础实现本身已经具备较好的并行访问和流水线能力。

### 2.6 原代码的主要性能瓶颈

原架构的主要问题不在 SHA-256 数学公式，而在阶段之间存在重复的数据搬运和控制：

- `preProcessing()` 先构造完整的 `SHA256Block`；
- `generateMsgSchedule()` 又花 16 个周期把块中的前 16 个字复制到 `W` 并写入流；
- 块数流和结束标志必须经 `dup_strm()` 复制给两个消费者；
- `blk_strm`、多组块数流及结束流增加了 FIFO、控制状态和阶段同步开销；
- 单个 SHA-256 核心只能顺序处理多条独立消息，消息级并行度没有被利用。

根据项目中的实验记录，原始测试工作负载的延迟为 **809 cycles**。

## 3. 我做了怎样的优化

## 3.1 优化一：合并预处理与消息调度生成

第一项优化是将 `generateMsgSchedule()` 的工作直接合并进 `preProcessing()`。

优化前的数据路径为：

```text
消息输入 → 生成 SHA256Block → 复制 W[0..15] → 扩展 W[16..63] → 压缩
```

优化后的数据路径为：

```text
消息输入 → 在预处理阶段直接生成并输出 W[0..63] → 压缩
```

具体变化包括：

1. `preProcessing()` 的输出由 `hls::stream<SHA256Block>` 改为 `hls::stream<uint32_t> w_strm`；
2. 读取原始消息字、大小端转换后，直接输出 `W[0..15]`；
3. 在同一个函数内用 16 字滑动窗口继续生成并输出 `W[16..63]`；
4. 对三种补位情况也直接产生完整的 64 个调度字；
5. 删除独立的 `generateMsgSchedule()` 阶段；
6. 删除 `SHA256Block` 中间流和用于复制块数信息的 `dup_strm()` 数据通路。

这样将原来的三级流水线简化为两级：

```text
preProcessing（分块、补位、消息扩展）
                    │
                    ▼
sha256Digest（64轮压缩、链式累加、结果输出）
```

这项优化的本质是 **算子融合与消除中间搬运**。它没有修改 SHA-256 算法，只改变硬件数据在模块间的组织方式。项目实验记录显示，延迟由 **809 cycles 降至 592 cycles**，减少：

```text
(809 - 592) / 809 × 100% = 26.8%
```

## 3.2 优化二：双核消息级并行

第二项优化是在外部接口不变的前提下，新增 `sha256_top_dual_core()`，内部实例化两个独立的 `sha256_top()` 核心。

整体结构为：

```text
                  ┌──────────────┐
              ┌──► SHA 核心 0    ├──┐
输入消息 ─► split_input           │  ├─► merge_output ─► 有序哈希输出
              └──► SHA 核心 1    ├──┘
                  └──────────────┘
                    order_core_strm
```

### 输入分配

`split_input()` 使用一个 1 位轮询变量 `rr`：

- 第 1 条消息发送给核心 0；
- 第 2 条消息发送给核心 1；
- 第 3 条消息再次发送给核心 0；
- 依此交替。

分配单位是**完整消息**，而不是拆分同一条消息，因此不会破坏 SHA-256 多数据块之间的链式依赖。每次分配还会把核心编号写入 `order_core_strm`。

### 输出保序

由于两条消息长度可能不同，后输入的消息有可能先计算完。`merge_output()` 按 `order_core_strm` 记录的核心编号，从对应核心读取结果，因此最终输出顺序仍与输入顺序一致。

### 对外接口保持不变

优化后的 `sha224()` 和 `sha256()` 仍保持原来的参数形式，只是内部默认转调双核版本：

```cpp
internal::sha256_top_dual_core<m_width, 256>(
    msg_strm, len_strm, end_len_strm, hash_strm, end_hash_strm);
```

因此上层 HMAC 代码和测试平台不需要修改。

### 效果与适用范围

双核主要提升的是**多条独立消息的吞吐量**，不会把同一消息内部有依赖的 64 轮压缩强行并行。对当前包含两条输入消息的测试，实验延迟由 **592 cycles 降至 433 cycles**，减少：

```text
(592 - 433) / 592 × 100% = 26.9%
```

双核的代价是 SHA 核心和配套 FIFO 的资源开销明显增加。在消息数量少、输入不连续或单条消息特别长时，收益也不会等同于理想的 2 倍加速。

## 3.3 优化三：FIFO 深度与存储资源分层

优化代码根据数据流用途重新配置了 FIFO。

单核内部最主要的调度字流配置为：

```cpp
hls::stream<uint32_t> w_strm("w_strm");
#pragma HLS STREAM variable = w_strm depth = 256
#pragma HLS RESOURCE variable = w_strm core = FIFO_BRAM
```

`w_strm` 每个消息块需要连续传输 64 个 32 位调度字，数据量最大，因此深度增加到 256，并指定使用 BRAM，减少大容量 FIFO 对 LUT 的占用。

块数和结束标志属于低带宽控制信息，配置为深度 128 的 LUTRAM FIFO：

```cpp
#pragma HLS STREAM variable = nblk_strm depth = 128
#pragma HLS RESOURCE variable = nblk_strm core = FIFO_LUTRAM
#pragma HLS STREAM variable = end_nblk_strm depth = 128
#pragma HLS RESOURCE variable = end_nblk_strm core = FIFO_LUTRAM
```

双核输入数据流深度设置为 256，长度流、哈希结果流设置为 64，顺序记录流设置为 128。这样可以缓冲不同阶段之间的速率波动，降低 DATAFLOW 因生产者和消费者节拍不一致而停顿或死锁的风险。

## 3.4 优化四：流水线、数组分区和内联控制

优化代码进一步明确了关键 HLS 指令：

- 预处理中的原始字读取、补位字生成和消息扩展循环使用 `PIPELINE II=1`；
- `sha256_iter()` 使用 `PIPELINE II=1`，指导工具以单周期启动间隔实现轮函数；
- `sha256_iter()` 使用 `INLINE off`，保留函数层次，避免过度内联扩大组合逻辑和关键路径；
- `W[16]`、`H[8]`、`K[64]` 使用完全数组分区，为同周期的并行访问提供独立寄存器资源；
- 顶层、双核顶层均使用 `DATAFLOW`，使预处理、压缩、输入分配和输出合并尽可能重叠执行。

第三阶段优化没有进一步降低当前测试的 433 周期延迟，但将估计时钟周期从实验记录中的 **12.882 ns** 改善到 **10.631 ns**，周期缩短约 17.5%，对应估计最高频率由约 77.63 MHz 提升到约 94.06 MHz。

## 3.5 评估后没有采纳的方案

实验记录中还评估了若干更激进的方案，但最终代码没有采用：

- **重排 SHA-256 状态更新**：`a` 到 `h` 的更新存在严格的数据依赖，错误重排会改变算法结果；最终代码仍保持标准轮函数的数学关系。
- **统一替换为非阻塞写入 `write_nb()`**：最终 `sha224_256.hpp` 中没有 `write_nb()`，仍采用确定性的阻塞式流读写，以避免增加复杂的回退控制和新的时序风险。
- **动态资源分配**：硬件中的静态资源配置更利于综合、时序分析和稳定复现，因此没有引入运行时动态分配。
- **过度细化尾部条件逻辑**：补位分支虽然较多，但属于算法正确性的关键部分，进一步复杂化控制的收益有限。

## 4. 优化前后对比总结

| 对比项         | 原代码                           | 优化代码                      |
| -------------- | -------------------------------- | ----------------------------- |
| 数据通路       | 预处理 → 消息扩展 → 压缩         | 预处理与消息扩展融合 → 压缩   |
| 前 16 个调度字 | 先存入块，再复制到 `W` 流        | 读取、转换后直接写入 `W` 流   |
| 中间块存储     | `SHA256Block` FIFO               | 已消除                        |
| 块数控制       | 通过 `dup_strm()` 复制给两个阶段 | 直接送入压缩阶段              |
| SHA 核心数量   | 1 个                             | 2 个                          |
| 多消息调度     | 单核顺序执行                     | 完整消息轮询分配到双核        |
| 输出顺序       | 天然顺序                         | 用 `order_core_strm` 显式保序 |
| 调度字 FIFO    | 深度 32，LUTRAM                  | 深度 256，BRAM                |
| 控制 FIFO      | 深度 32                          | 深度 128，LUTRAM              |
| 外部接口       | `sha224()` / `sha256()`          | 保持不变                      |
| 测试延迟       | 809 cycles                       | 433 cycles                    |
| 估计时钟周期   | 实验中间值 12.882 ns             | 10.631 ns                     |

从 809 cycles 到 433 cycles 的总体延迟降幅为：

```text
(809 - 433) / 809 × 100% = 46.5%
```

需要注意，项目记录中曾把“809 降至 433”写成“提升 26.9%”；26.9% 实际对应的是第二阶段从 592 降至 433，完整优化相对最初版本的正确降幅应为 **46.5%**。

- C/RTL 协同仿真：Verilog `Pass`；

- 两组 HMAC-SHA256 输出均与测试平台的黄金结果一致。

这说明优化没有改变 HMAC-SHA256 的计算结果，且生成的 RTL 与 C 模型行为一致。

### 5.3 HLS 综合资源

根据当前目录中的 `csynth.xml`：

| 资源     | 使用量 | 器件可用量 |   占比 |
| -------- | -----: | ---------: | -----: |
| BRAM_18K |     94 |        280 | 33.57% |

| LUT      | 31,477 |     53,200 | 59.17% |
| DSP      |      0 |        220 |     0% |

资源结果符合本次“以资源换性能”的设计方向：双核和深 FIFO 提高了 BRAM、FF、LUT 使用量，但仍未超过目标器件的可用资源，且完全不使用 DSP。

### 5.4 当前实现的注意事项

C 仿真日志中存在如下警告：

```text
hls::stream 'end_hash0_strm' contains leftover data
hls::stream 'end_hash1_strm' contains leftover data
```

当前测试和协同仿真均已通过，因此该警告没有影响本次两组数据的正确性。其原因是 `merge_output()` 按顺序读取每条有效哈希及其 `false` 标志，但结束后没有继续消费两个子核心各自留下的最终 `true` 结束标志。若后续把模块改成长时间运行、多批次重复调用或更严格的数据流仿真，建议在合并阶段显式排空两个子核心的终止标志，避免残留数据造成潜在挂起。

## 6. 最终结论

本次优化没有改变 SHA-224、SHA-256 及上层 HMAC-SHA256 的外部接口和算法结果，而是从硬件数据通路入手完成了四项改进：

1. 将消息调度生成融合进预处理，消除 16 周期复制阶段和多余中间流；
2. 使用双 SHA 核心并行处理不同消息，通过轮询分配和顺序标记保证输出有序；
3. 按数据流用途调整 FIFO 深度，并将大容量调度字流映射到 BRAM；
4. 结合 DATAFLOW、PIPELINE II=1、ARRAY_PARTITION 和 INLINE off 改善吞吐与关键路径。

最终在当前两输入 HMAC-SHA256 测试中，将延迟从 **809 cycles 降至 433 cycles，整体下降 46.5%**；估计时钟周期达到 **10.631 ns**。C 仿真与 RTL 协同仿真均通过，证明优化后的实现兼顾了功能正确性与性能提升。
